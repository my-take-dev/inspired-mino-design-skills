# Runtimeと保守資料の分離

## 依頼と根拠

2026-09-16の利用者指示: 品質を落とさず全文読込の負荷を解消し、人物・生成モデル名、作成時の判断・履歴をSkill外へ移す。呼出名の変更回答は未受領のため、既存`mino-*`は互換識別子として維持する。

根拠は[設計知識のモジュール化](../../mino-doc/19-skill-modularization-and-scaling.md)と[前回試用の記録](../../mino-doc/31-practicality-refresh-20260910.md)。節を選ぶ指示だけでは、全文取得・出力省略・再読が起きた。判断本文とschemaが同一fileにある構造を変更する。

## 判断

| 観測・制約 | 採用した変更 | 品質の保護 |
|---|---|---|
| 入口から大きな共通文書とworkflowを読む | 固有手順・gate・subject判定をSKILLへ集約 | 条件owner、失敗保証、12観点、authority、移行・復旧を残す |
| 通常回答で保存schemaも展開される | schemaを別fileにし、正本packageだけからrouting | 旧schemaの991 fieldを保守側contractと比較 |
| 配布内に評価履歴・出自・設定資料がある | maintenanceへ移設。元調査はmino-docに保持 | runtimeから外部資料への依存を作らない |
| 欠陥と未知の扱いを軽量化で失う危険 | 共通Evidence・承認・次phase・releaseを維持 | 比率・ID・既知gap/unknown・未実行を試用で点検 |
| 回答ファイル保存がplatform全読込を誘発 | 対象systemの操作・複数OS条件だけで追加読込 | 正本packageのplatform schemaと必要なruntime検証は保持 |

## 契約の差分

- 共通規則の出自はsource-derived principle、suite operationalization、repository policyとしてこの保守領域で管理する。対象業務の根拠を表すEvidenceはruntimeに残す。
- `implementation_spec.method_provenance`、`reproducible_development_result.method_provenance`、`completeness_package.audit_rubric.name/origin`を除去。audit_rubric.dimensionsは保持する。
- decision内のplatform記述を共通schema参照へ統合。必須のunknown、runner、command、ownerは保持する。
- validatorの必須見出しをAGENTSの5見出しへ統一する。mode・authority・実行方針は本文と共通規則に保持し、mode/enum/owner/subject verdictの機械検査は維持する。
- execution-profileとruntime-compatibilityは通常の設計作業に不要な作成・実行環境側の責務。実行設定の選択・モデル名・API対応説明をruntimeから外す。設定互換性だけのC36/C37/C46は現行oracleでsuite非適用とする。C29/C38の採点表現も新しい責務へ合わせる。
- 統合の非該当専門packageはfunction_planに理由がある場合のみ省略可能とする。該当packageはfieldまたはfunction_artifact_refsへ解決し、ID・owner・coverage・未知を保存する。mode_artifact.kindは表示名でなく機械enumを使う。
- suite versionは0.12.0を維持。新評価revisionは0.12.0-r5、57ケース。旧case/oracleは移設前と同じbytesを保持する。
- entryと共通規則の14,000 bytes上限、schema早期展開、作成人物・モデル名、履歴・保守payloadの混入を検査する。既知文字列検査だけで未知の固有名詞を網羅できるとは主張しない。本文も点検する。

## 試用からの修正

初期候補C47は未知をpresentにせずN/Aを共有できたが、未知の処遇を記録したcellまで未screenとして数えた。未知なmodel elementへ根拠付きで接続すればscreen済み、実在coverageには含めないことを明記した。

C56では要件の制約記述をmodelの保証済み根拠へ昇格する問題を検出した。presentには対象modelの定義・code・観測を必要とする説明を追加し、別contextの再試行で制約違反を充足から除外した。

品質比較C53と統合C54は再読・出力省略なし。C53は回答保存だけでplatform referenceを読んだため、本文のtriggerを対象systemの操作へ限定した。正本packageは必要schemaを読むため通常回答より多い。この量を削るために条件ownerやoracleを落とさない。

## 反映手順

自動承認レビューが未検証の一括上書きと検証契約変更を拒否したため、候補をリポジトリ外で完成させた。参照解決、旧field比較、回帰fixture、独立した試用の結果を揃えてから同じ候補を反映する。試用のscope制約はOSによるoracleアクセス遮断とは異なり、release runには数えない。

検証と残存事項は[評価記録](../evaluations/0.12.0-r5.md)に分離する。
