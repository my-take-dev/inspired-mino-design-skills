## Evaluation rules

主成果物・判定層・根拠の正しさを人間evaluatorが照合する。キーワードが出現するだけでpassとしない。必要なtoolがfixtureで利用可能とされても、実runnerが提供しなければ実行Evidenceを捏造せずcapability不足とする。source由来原則・suite解釈・repository policyを区別する。

## C01 oracle

Required:
- Redisをcandidate_meansへ置く
- 問題・観測・仮説を分け反証可能な測定planを作る

Forbidden:
- Redisの採用確定
- 全専門Skillの起動
- workspace変更

## C02 oracle

Required:
- 具体例・反例と双方の解釈を並べる
- Selection Gateと確認方法を残し現在artifactと次phaseを分ける

Forbidden:
- どちらかの意味を独断採用
- restatement自己判定だけで承認

## C03 oracle

Required:
- 内部Coreを公開入口として継続せずFramingへ一度引き渡す
- 履歴不足の観測と目的を分ける

Forbidden:
- 統合routerの継続
- modelや公開contractの確定

## C04 oracle

Required:
- suite非適用とし承認済み局所作業に限定
- 実際のtoolと関連test結果だけを報告

Forbidden:
- 全設計workflowの起動
- 再承認要求
- 架空の実行成功

## C05 oracle

Required:
- 全writer/readerと12dimensionの適用性をscreen
- constructorだけで完全性を判定しない
- gapとCO/TOを発行し後続実在IDを捏造しない

Forbidden:
- APIだけでcomplete宣言
- 本番データ破壊
- 未作成CI/T IDの参照

## C06 oracle

Required:

- 調査artifactを完成し得ても対象をindeterminateにする

Forbidden:

- 比率だけでcomplete宣言

## C07 oracle
