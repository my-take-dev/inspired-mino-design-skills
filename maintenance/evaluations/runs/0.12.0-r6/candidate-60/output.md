境界案は `separated`、設計回答は `ready`。案の採用状態は `proposed`。

B1 r3の「個人文書は現在同じプロジェクトに所属する利用者だけが閲覧でき、退会後は拒否する」をそのまま使う。文書管理責任者によるRV1の `accepted` reviewと採用済みの判断が、今回の個人文書・利用者種別・revisionを覆う。意味差分はなく、再承認は不要。

- 公開面：`read_document`。利用者と対象文書を指定し、閲覧可能ならメモリ上の文書を返し、認可条件を満たさなければ拒否する。副作用はない。呼出側はこの操作・結果・拒否条件を知る。
- 内部：所属の参照方法、文書のメモリ表現、取得手順を隠す。現在所属の判定と拒否を操作の内側に集め、呼出側へ認可分岐を配らない。意味のauthorityはB1 r3と文書管理責任者の既存判断を参照する。
- 構造：呼出側は操作契約に依存する。実在variantは提示されていないため、選択用factoryや将来用の階層は設けない。

| 操作の意味 | 適用判断と根拠 |
|---|---|
| end_to_end_deadline | `not_applicable`。今回のメモリ参照境界に期限要求は提示されていない。上限やtimeout結果を追加しない。 |
| retry_semantics | `not_applicable`。外部I/O・外部障害回復がなく、自動再試行を設ける根拠がない。 |
| idempotency | `applicable`。状態を変更しない。認可状態が変われば結果は変わり得るため、以前の成功は次回の閲覧許可を保証しない。操作側がB1 r3を維持する。keyは不要。 |
| duplicate_semantics | `applicable`。重複呼出しもその時点の所属条件に従う。退会後の呼出しは拒否する。操作側が保証する。 |
| ambiguous_outcome | `not_applicable`。保存・外部I/O・状態変更がなく、外部への反映成否を照合・復旧する対象がない。 |

実装交換時も公開契約を維持できる境界として設計上 `pass`。variant追加と業務規則変更は今回 `not_applicable`。結果を変える意味の未知は入力上なし。実装・テストは未実施で、実装の適合性を検証済みとはしない。後続で実装する場合は、実装担当が対象環境のtest runnerで在籍中の成功・非所属の拒否・退会後とその再呼出しの拒否を確認する。runnerとcommandは対象code提示後に特定する。
